# Aggressive Recursive Orchestration

This skill counterbalances a shallow-graph default. It changes decomposition
and routing pressure only. `$adaptive-orchestration` still owns consumers,
waiting, verification, recovery, authority, and shared-state safety.

It grants no authority, capacity, spend, model availability, or required agent
count. Repository and user contracts remain authoritative.

## Decomposition audit

Before direct work on a non-trivial task:

1. Bind the objective, acceptance evidence, authority, dependencies, and
   shared mutable surfaces at the highest useful owner.
2. List unresolved artifacts, hypotheses, evidence sources, implementation
   shards, and review lenses.
3. Admit a branch only when it has a distinct contract, a named consumer, and
   credible marginal value in uncertainty reduction, latency, evidence quality,
   context isolation, or risk containment.
4. Re-run the audit after material evidence, refusal, recovery, or constraint
   change. Propagate this requirement to non-leaf children while useful splits
   remain.
5. Work directly only after recording why: no positive-value split remains, a
   shared mutable critical section remains, or real authority/capacity blocks
   expansion.

Fan out broadly for independent read-only discovery, contradictory hypotheses,
test mapping, or review. Fan in before ordinary repair. Then mutate through
the minimum sufficient set of non-overlapping writers. Do not create agents to
reach a count, replicate a branch, or enforce a fixed hierarchy.

## Route capability deliberately

Before every child dispatch, choose its model and reasoning effort explicitly.
Optimize expected time and cost to correct acceptance, not the cheapest
individual call. Give headroom to unresolved ambiguity, consequence,
downstream fan-out, or likely rework; downshift settled deterministic work.

Pass a compact edge packet: bound root/candidate, scope, remaining question,
acceptance evidence, consumer, authority limits, and escalation trigger. Do
not silently rely on inherited history or routing. If telemetry exists, report
requested and observed routing separately.

If a requested route is unavailable or its effective route cannot be observed,
say so and inherit only when continuity or the unresolved risk justifies it;
otherwise choose an available sufficient route. Never invent an observed model
or reasoning value.

## Ownership shape

Each child returns to its immediate owner. Cross-cutting decisions return to
the nearest owner with sufficient scope. `role != thread != model != authority
!= spend`.

Use multiple independent reviewers only when their lenses and consumers are
materially distinct. Validate through substantial real work, not synthetic
fan-out. Measure usefulness by accepted critical-path progress, independence,
evidence quality, and duplicate avoidance—not width or depth.
